从原件到检索证据

售后同事问「AB-123 温度传感器报警怎么处理」。系统需要找对型号和步骤，并让同事打开手册核对。沿着这个查询了解 InkRAG Core，从原件、解析和入库走到检索策略、来源和故障诊断。

页内实验使用合成材料，可以离线操作。各章分别标明实际代码、运行入口和应检查的结果。

目标与证据

先约定一条正确答案需要什么证据。RAG 是检索增强生成，也就是先从指定资料找证据，再把证据交给模型组织回答。

首版约定三种可观察结果。命中时返回正确型号的原文和出处。证据不足时明确表示查无可用证据，例如从未入库的 AB-1239。执行失败时返回可定位的错误，例如向量服务超时。空命中、依赖失败和权限拒绝应有不同的状态。

先把「问句 → 证据」跑通，再加入回答生成。比如首版搜到的原文是「先断开电源」，结果里要能检查文件名、页码或元素定位。模型的回答只是基于原文整理出的文字，检索命中的片段和固定版本才是可回查的证据。

架构与状态

入库把一份手册变成可查询的片段。查询把一句话变成有出处的证据。理解这两条线以后，再换其中的解析器、分词器、嵌入模型或数据库。

跟着一份手册走
责任输入和输出谁持有状态
解析和分块从原件或交换 JSON 得到正文、表格内容、页码或元素引用，按配置准备片段。原件和解析产物由调用方保管。
分析和嵌入分词器把文字变成词项和规范化编号。嵌入模型把文字变成指定维度的向量。索引绑定词项规则和模型身份。片段原文仍用于展示与引用。
存储与召回写入片段、词项与向量。各检索通道在给定范围内读取候选。SQLite 持有本地数据；共享数据库使用 PostgreSQL 和 pgvector。
策略和融合根据问题执行一次查询或有限步骤，合并排名并返回证据与阶段诊断。查询预算和来源范围由调用方设置，证据沿片段引用回到原件。

配置、调用与存储方案

解析与分块

同一句说明可能来自 PDF 段落、Word 表格或扫描图片。先把内容和出处一起读出来，再决定哪些内容应放进同一个片段。

  1. 保留原件。把原件保存到可回查的位置。修订时用新解析版本保存变更，审阅时仍能核对同一原件和旧版本。
  2. 解析为结构。inkparse.Parser 接收 ParseRequest，输出带 result_id 的 ParseResult，包含结构元素、来源和诊断。纯文本有可用的内置读取器，文本 PDF 可提取文本层。扫描图片需要适合的 OCR 能力。Docling 属于可选解析器，运行环境与工件见解析手册。
  3. 准备证据片段。切分时让每段保留能回到原文的定位。对表格，优先保证值与列名或必要上下文能一起查到。选择分块单位时阅读对应切分器的文档，长度、重叠和模型输入预算都受单位影响。
读代码 · 从 JSON 到可回查的片段 
from inkrag_core import ParsedDocument

# Core 的交换 JSON 保存每段原文、元素定位以及已有页码。
parsed = ParsedDocument.from_json(path.read_bytes())

# 保持同一个资料 ID，整个资料的片段随此次写入一起替换。
chunks = engine.ingest("manual-ab-123", parsed)
for chunk in chunks:
    print(chunk.source.name, chunk.source.page, chunk.source.element_ref)

document.py 先验证 JSON，再按 Part 切成片段。默认切分按字符计量，CharacterChunker(600, 80) 表示片段最长 600 个字符，相邻片段可重叠 80 个字符。嵌入模型以 token 限制输入时，要结合实际 tokenizer 调整长度或注入自己的切分器。

用 InkparseAdapter().load(path) 接已有 InkParse 结果，保留其结果身份和原件摘要。页面和元素引用是回查线索。应用需要保有相应原件或解析包，才能让链接实际打开。

实验 · 改变分块边界

实验按句合并，突出边界对一条证据的影响。

2 句
两句一组且无重叠时，断电和检查接头分在不同片段。

片段太短时，故障条件可能和处理步骤分开。片段太长时，一个候选会混入多个主题。重叠能保留跨边界上下文，也会增加重复命中和向量计算量。先拿同一组问题比较分块，再确认引用能定位到正确元素。页码只在原格式提供时使用，Markdown 或 TXT 的来源可通过原件和元素引用回查。

中文关键词检索

关键词一路先确定哪些片段匹配，再把候选排序。分词决定拿什么匹配，BM25 负责给已经匹配的片段打分。

BM25通常给稀有词更高的权重，也会考虑词在片段里出现的次数和片段长度。比如库里每一篇都写「处理」，只有少数写「温度传感器」，后者更能区分资料。重复出现会增加贡献，增加幅度会逐渐减小。

编号适合独立保存。把 AB-123 切成「AB」和「123」时，另一个相似型号可能也匹配。只查型号时使用完整规范化值做精确判定；带型号的自然语言问题还需要保留正文关键词和原句语义。Core 的索引侧和查询侧使用配对的规则，换分词器时先重建受影响的索引。

向量、融合与评测

用户说「测温探头告警要怎么处理」时，手册可能只写「温度传感器报警」。向量路补这类措辞差异。

入库时把每个原文片段送进嵌入模型，得到一组数字。查询时用同一模型把原问题变成向量，再找距离近的片段。即使两个模型维度一样，向量坐标的含义也可能不同。索引绑定模型身份和维度，换模型需要重新索引。具体型号和授权范围仍由查询约束。

RRF 按排名融合。某个片段在一路第 r 名，贡献 1 / (k + r)，另一条路也命中就再加一份。下面从 k=60 起算，观察一个片段怎样因为两路都命中而前移。

先评召回，再评回答

给每个问题标出必须看到的证据组。比如「断电之后做什么」需要处理步骤，而「什么时候要校准」需要控制板更换这一条件。前五证据组覆盖能判断有没有把依据找回来，首个相关证据的排名能判断用户要翻几条。另测未知型号、旧版误引、撤销资料和请求失败。模型生成的答案再核对断言和引用是否对应。候选数量、分词和融合参数每次只改一个，保留逐题的命中与退步。

图与分步检索

「北区 AB-123 的延保找哪个团队」需要三份证据。先找到适用型号，从政策找到受理站，最后从服务名录找到团队。

什么时候引入多个步骤
策略适合的输入要检查的停止原因
图检索已登记的实体和关系都有原文片段。给出起点，沿关系展开。路径缺证据、证据超出范围、访问深度或边数用尽。
问题分解各子问题预先可知，例如分别查适用地区和退货期限。子问题重复、步骤已执行完或达预算。空结果也需要检查。
迭代检索下一问依赖前一步，如确认受理站以后再查团队。回调决定结束、问题重复或触发预算。何时证据已经足够由调用方判断。

实验 · 一条关系何时可用

教学路径从 AB-123 开始。用深度和范围查看能取得哪些原文，只对这条路径计证据。

2 条
两条边可以到达受理站。第三条边才能找到团队。

先将每条边记录成「起点、关系、终点、片段身份」。再给遍历设深度与候选预算。受范围限制的边不能作为跳板，否则终点即使有权可见，也可能泄露中间的关系。知识变更后检查旧片段身份是否还有效。

Core 的图路径适合已明确登记的局部关系。对照组先用相同原件做一次混合检索，比较是否真的补回了成组证据。要做跨全库的全局主题总结，需另行评估关系抽取、聚类摘要和引用验证。

既有 SDK 的本地练习与真实模型

既有 inkrag.RAG 示例使用 MockEmbedding。真实执行的是解析、分块、FTS5 检索、保存和重开。

uv run --locked --package inkrag --no-dev python - <<'PY'
from pathlib import Path
from tempfile import TemporaryDirectory

from inkrag import RAG
from llama_index.core.embeddings import MockEmbedding

model = MockEmbedding(model_name="learn-demo", embed_dim=4)

with TemporaryDirectory(prefix="inkrag-learn-") as tmp:
    root = Path(tmp)
    manual = root / "manual.txt"
    manual.write_text(
        "AB-123 温度传感器报警时，先断开电源，再检查接头。",
        encoding="utf-8",
    )
    with RAG.open(
        root / "knowledge", embedding=model, lexical_profile="jieba-v1"
    ) as rag:
        receipt = rag.ingest(manual, document_id="manual")
        print("片段数", receipt.node_count, "快照", receipt.snapshot_id)

    # 重开后查询会读取快照的词项规则。
    with RAG.open(root / "knowledge", embedding=model) as rag:
        result = rag.retrieve("ab-123", mode="keyword")
        assert result.snapshot_id == receipt.snapshot_id
        assert result.hits and "断开电源" in result.hits[0].get_content()
        assert not rag.retrieve("AB-1239", mode="keyword").hits
        print(result.hits[0].get_content())
        print(result.hits[0].metadata)
PY

沿诊断排查

客户说「测温探头报错，怎么恢复？」检索只给了另一个型号。先找失效阶段，再改具体规则。

从事实到候选再到排序
先观察什么下一步验收反例
解析包有没有该句在原页对照，检查所选引擎、警告、阅读顺序和表格结构。删掉该页正文或输入损坏包，区分解析失败和可搜索正文为空。
正确片段有没有写入核对资料身份、版本、片段原文和来源。步骤拆散时改切分策略。更新同一资料后，旧步骤不再被当前检索返回。
哪一路取得候选看编号是否完整，词项是否匹配，向量模型与索引是否一致。用相邻型号、同义问法、错误模型和越界的资料范围复测。
融合前有，融合后没有保存通道名次、候选深度和最终 Top K。先确认是否要调整范围或候选预算。真实漏召回有改善，同时已正确的证据不掉出前 K。
请求中断或写入失败区分失败阶段及提交结果。回读已有资料，查实际版本，再决定是否重试。注入嵌入或数据库失败，旧资料仍可查；关闭重开后继续正确查询。

依据诊断复测时固定原件、模型、筛选范围和最终 Top K。把问题、应该命中的证据组和禁止出现的证据一起记录，方便后续比较。

读代码 · 从查询入口进入策略和事务
  1. 在 engine.py 找 Engine.retrieve()，查看输入校验、路由和范围。Index.read() 在一次查询中固定快照，防止词项、向量和图读到不同批次。
  2. 定位 SearchResult.steps。找到关键词已召回却在最终结果缺席的片段，核对候选名次、融合与最终 Top K。没有候选时返回分词或原文排查。
  3. 切换到 Engine.ingest()。批量准备和校验词项与向量以后才调用 Index.replace()，存储事务负责同资料的整体替换。模拟第二个嵌入批次失败，观察上一个版本仍可查。
  4. 如果要换分词器，只改组装时注入的分析器，为新规则使用新的标识和集合。同一问集在两个集合复跑，逐条对照证据。

索引变更与恢复

既有工作台与发布

多人使用时，上传可能排队、模型可能失败，客服仍需查询上一版。这一章关注谁能改状态，以及查询怎样始终读到一个确定版本。

  1. 提交。HTTP 从已验证的身份获得租户和角色，校验资料归属。原件写入资产存储，资料、任务及待投递事件一起记录在 PostgreSQL。202 表示请求已受理。
  2. 处理。Relay 将待投递事件送给 RabbitMQ，Worker 按任务租约处理。解析产出固定版本，后续构建按输入清单切分和生成向量。索引是派生数据，原件、解析版本和发布记录是追溯依据。
  3. 试查与生效。Worker 在独立 OpenSearch 候选写索引，等待写屏障、刷新并核对清单。候选可试查，正式发布由 PostgreSQL 条件更新指针。自动生效和手动发布都要核对候选及当前状态。
  4. 查询与引用。查询开始时固定一个发布和索引版本，应用可信范围和当前撤销条件。结果记录 trace_id 供定位。引用对应资料、解析版本、元素和可用页码。回滚会切换到可用的旧版本，已经撤销的资料仍受当前限制。

实验 · 同一问题读哪一版

状态演示。V1 写「检查接头」，V2 补了「记录故障灯状态」。尝试构建失败、发布和回滚。

线上读 V1，构建中的候选暂不可试查。

网页走 HTTP，Python 查询同一个已发布库可走 RAG.open_published()，两条入口复用平台查询逻辑。Worker 和本地 SDK 共用片段准备，采用 jieba-v1 时共用切词与编号规则。本地 SQLite 和平台 OpenSearch 各自执行索引、存储和排名。查同一平台发布可以对比两入口的命中顺序，本地库与平台库要按同一验收案例比较行为。

回答如何引用证据

平台启用回答模型时，/api/v2/knowledge-bases/{kb_id}/answers 先走同一条检索链路，再把命中原文切成可引用的小段。模型给出的每条陈述附来源和段落编号，服务核对编号存在并回填同次检索的原句。没有可用证据时返回 insufficient。生成后还会核对权限与当前发布，避免查询途中撤销的数据从答案泄露。

例如，模型若用第 2 页的「先断开电源」作出处，却写成「先检查接头再断电」，引用位置存在，回答顺序仍有错。验收时应同时检查陈述和引文是否一致。 回答与引用校验源码

跟 AI 搭自己的系统

从两份可以公开的手册和三个有标准答案的问题起步。先建立可运行、可读懂、可重开的闭环，再按验收结果扩大范围。

  1. 你定目标。写出谁来用、最常查什么、什么错误代价高。明确资料和权限边界，给一条应该命中的问题与一条必须为空的反例。
  2. 让 AI 走第一条线。要求它先读现有入口，说明原件、片段、索引和引用各在哪里。先实现一类文件和一个查询入口，用输出原文及出处验证闭环。
  3. 按证据改一处。编号串错先看词项和匹配条件，专业词漏掉先查分词，步骤缺失先查原文和分块。保持其他配置一致再对照。
  4. 把接手方法留在项目里。要求说明安装、配置、运行入口、失败和恢复方法。让每次改动都能从一个业务例子追到源码位置，再追到测试证据。

我有 AB-123、AB-1234 两份不同手册。使用 InkRAG Core 和 SQLite 做一条可重开的检索链路，输出片段和原文位置。先读公开入口，用一张图画出解析、分块、词项、向量和查询经过的数据。先跑基线，再只修改一条分词或切分规则。用正确型号、近似型号、未知型号和一次故障比较改变前后的前五证据与出处，留下可复现命令。

开发者要懂到什么程度

能独立画出一条请求从输入、持久化到输出的路径，说清楚哪份数据是事实，哪份索引能重建。能在一个错误例子里分辨解析、切分、候选召回、排序、权限或模型故障，并指出下一次要看哪条证据。能判断一次改动会影响哪些调用方和旧数据，能解释发布失败时为什么旧版本仍可用。

这些判断必须由开发者掌握，因为谁能读资料、错误要付什么代价、什么结果可以发布，都取决于人的业务责任。AI 可以写适配器、生成测试夹具、找反例和跑回归。开发者定义成功条件，挑选有代表性的反例，检查实际输出和证据，再决定是否合并或上线。

这条学习闭环验收的是指定样例上的功能和理解。扩到团队使用时，再拿真实业务资料、实际调用方、并发和恢复演练检验容量与运行质量。
